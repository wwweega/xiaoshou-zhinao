## 坑 1 · TraceRecorder 放进 GraphState 导致序列化崩溃

### 现象

```
TypeError: Type is not msgpack serializable: TraceRecorder
```

工作流跑到第二个节点就崩，报错点不在业务代码，而在 LangGraph 内部。

### 根因

最初的设计里，我把 `TraceRecorder`（链路追踪器）直接塞进了 `GraphState`：

```python
class GraphState(TypedDict):
    task: str
    plan: Plan
    results: list
    _tracer: TraceRecorder   # ← 问题在这
```

LangGraph 的 Checkpointer 机制会在**每个 super-step 结束后序列化整个 state**
（为了支持断点续跑），序列化器是 msgpack。而 `TraceRecorder` 内部持有
`threading.Lock`、`list[Span]` 等运行时对象，msgpack 无法处理。

这是**职责混淆**的典型表现：

| 数据类别 | 例子 | 是否该进 state |
|---|---|---|
| 业务数据 | 任务描述、计划、子任务结果、评分 | ✅ 必须进，且必须可序列化 |
| 运行时观测数据 | 追踪器、日志句柄、连接池、锁 | ❌ 绝不进 state |

state 是**可持久化的业务事实**，追踪器是**进程内的可观测性副作用**，两者生命周期完全不同。

### 修复

新建 `app/core/context.py`，用 Python 标准库 `contextvars` 承载追踪器：

```python
import contextvars

_tracer_var: contextvars.ContextVar = contextvars.ContextVar("tracer", default=None)

def set_tracer(tracer) -> contextvars.Token:
    return _tracer_var.set(tracer)

def get_tracer():
    return _tracer_var.get()

def reset_tracer(token) -> None:
    _tracer_var.reset(token)
```

`contextvars` 的关键特性：**在 asyncio 中每个 Task 持有独立的上下文副本**，
因此并发任务之间不会串扰，同时又能被同一 Task 内的所有协程（包括嵌套的 Agent 调用）读到。

工作流中改为：

```python
async def run(self, task: str):
    tracer = TraceRecorder()
    token = set_tracer(tracer)
    try:
        state = await self.graph.ainvoke(initial_state)
        return state, tracer
    finally:
        reset_tracer(token)   # 必须 reset，否则污染事件循环
```

`GraphState` 里彻底删掉 `_tracer` 字段。

### 实践意义

**Q: 为什么不用全局变量？**

> 全局变量在 asyncio 并发下会互相覆盖 —— A 请求的 span 会被 B 请求写进去。
> 也和"请求级隔离"的架构目标冲突。`threading.local` 也解决不了，因为 asyncio
> 是单线程多协程，同一线程内多个协程共享 `threading.local`。
> `contextvars` 正是 PEP 567 为此设计的：协程级隔离，语义等同"异步版 thread-local"。

**Q: Checkpointer 和状态可序列化性是什么关系？**

> Checkpointer 是 LangGraph 实现 Human-in-the-loop 和断点续跑的基础设施，
> 它按 super-step 粒度做快照。这个约束反过来强制我们做**状态分层**：
> 能进快照的必须是纯数据。这其实是好事 —— 它逼你把"状态"和"副作用"分开，
> 也是分布式工作流引擎（如 Temporal）的通用设计。

## 坑 2 · 工具执行返回 `ok=True`，但实际已被安全策略拒绝（最严重）

### 现象

单元测试中执行 SQL 注入用例：

```python
result = await registry.call("sql_query", {"sql": "DROP TABLE orders"})
```

日志里明确打印了 3 次 `PermissionError: 检测到破坏性 SQL 语句，已拒绝执行`，
但断言拿到的是：

```python
assert result.ok is True      # ← 竟然通过了？！
assert result.error is None   # ← 也是通过
```

**安全拦截形同虚设。** 如果这个问题上了生产，SQL 注入防护会 100% 失效 ——
调用方看到 `ok=True` 会认为查询成功，进而把 `result.result`（实际是 None）当数据用。

### 根因

`ToolCall` 数据类的字段默认值：

```python
@dataclass
class ToolCall:
    ok: bool = True          # ← 默认 True
    result: Any = None
    error: str | None = None
```

而 `call()` 内部的重试循环是这样的：

```python
for attempt in range(max_retries):
    try:
        record.result = await spec.func(**arguments)
        record.ok = True
        break
    except (PermissionError, ValueError) as exc:
        last_err = f"{type(exc).__name__}: {exc}"
        metrics.tool_errors += 1
        break                # ← 只 break，没有把 ok 置为 False！
```

`break` 跳出循环后，`record.ok` 仍然保持默认的 `True`。末尾的
`if not record.ok: metrics.tool_errors += 1` 自然也不会触发。

**这是"依赖默认值"写代码的经典陷阱** —— 默认值 `True` 在正常路径下是对的，
但在异常路径下变成了一个沉默的错误承诺。

### 修复

不再依赖任何默认值，改用**"是否真的拿到结果"作为唯一判据**：

```python
# 循环结束后统一裁决，不信任中途的赋值
if record.result is None and record.error is None:
    record.ok = False
    record.error = last_err or "工具执行失败且未返回错误信息"
elif last_err is not None and record.result is None:
    record.ok = False
    record.error = last_err

if not record.ok:
    metrics.tool_errors += 1
```

同时补了针对性回归测试（`tests/test_core.py::TestToolSecurity`）：

```python
async def test_sql_injection_rejected(self):
    r = await registry.call("sql_query", {"sql": "DROP TABLE orders"})
    assert r.ok is False
    assert "PermissionError" in r.error
    assert r.result is None
```

### 实践意义

**这是全项目最有讲头的坑，因为它同时涉及三个考点：**

1. **防御性编程**：默认值即"隐式契约"。当异常路径和正常路径共用同一个对象时，
   默认值会掩盖失败。正确做法是让"失败"成为需要**显式声明**的状态，
   而不是"忘记修改默认值"的结果。（延伸：Rust 的 `Result`、Go 的 `err` 都是这个思路）

2. **静默失败比崩溃更危险**：崩溃能被监控发现，静默失败会被当成成功数据进入下游。
   金融、风控、电商场景里，一次静默失败可能造成真实资损。

3. **测试的价值体现在这里**：如果我写的测试是"能跑通就行"，这个 bug 永远发现不了。
   真正有用的测试用例是**对抗性的** —— 故意传注入串、故意传错误参数，
   断言的是"必须失败"，而不是"应该成功"。

**Q: 你会怎么从架构上彻底避免这类问题？**

> 让 `ToolCall.ok` 不设默认值，强制构造时必须显式传入；
> 或者更彻底 —— 用 `Result[T, E]` 类型（成功/失败二选一），
> 让"既没结果也没错误"这种状态在类型层面不可表达。
> Python 里可以用 Pydantic 的 discriminated union 近似实现。

## 坑 3 · 安全异常被当成可重试异常，白等 1.3 秒

### 现象

SQL 注入用例虽然最终被拦下了，但耗时 1.3 秒，日志里同一条 `PermissionError`
打印了 3 次。也就是说：**被安全策略明确拒绝的操作，系统还在傻等它重试成功。**

### 根因

重试装饰器的异常分类过于粗糙，把所有异常都当成"可能瞬时失败"：

```python
except Exception as exc:
    last_err = str(exc)
    await asyncio.sleep(backoff)
    continue          # ← PermissionError 也被重试了
```

这在语义上是错的。**重试的前提是"失败是瞬时的、且重试可能改变结果"**，
而 `PermissionError`（安全拒绝）和 `ValueError`（参数非法）是**确定性失败**：
输入不变，结果永远不会变。重试只是浪费时间和配额。

### 修复

按"失败是否可恢复"对异常分类：

```python
except (PermissionError, ValueError) as exc:
    # 确定性失败：安全拒绝 / 参数非法，重试无意义
    last_err = f"{type(exc).__name__}: {exc}"
    break
except TypeError as exc:
    # 调用签名错误，属于代码缺陷，重试也是错
    last_err = f"{type(exc).__name__}: {exc}"
    break
except asyncio.TimeoutError:
    # 瞬时失败：网络抖动、下游慢，值得重试
    last_err = "TimeoutError: 工具执行超时"
    await asyncio.sleep(backoff)
    continue
except Exception as exc:
    # 未知异常：保守起见重试一次
    last_err = f"{type(exc).__name__}: {exc}"
    await asyncio.sleep(backoff)
    continue
```

### 实践意义

**Q: 你怎么设计重试策略？**

> 分三步：
> ① **分类**：确定性失败（4xx、参数错、权限错、校验错）不重试；
> 瞬时失败（超时、429、5xx、连接重置）才重试。
> ② **退避**：指数退避 + 随机抖动（jitter），避免重试风暴同时打崩下游。
> ③ **熔断**：连续失败 N 次后打开熔断器，快速失败而不是持续重试。
>
> 本项目用了 tenacity 做 LLM 调用重试，工具层手写了简化版，
> 因为工具层需要按异常类型精细分流，用声明式装饰器反而不好表达。

## 坑 4 · 参数校验依赖 `TypeError`，导致非法参数被静默忽略

### 现象

```python
result = await registry.call("competitor_scraper", {"wrong_arg": 1})
# 期望：报错，告诉我参数名不对
# 实际：ok=True，静默用了默认参数跑完了
```

### 根因

`competitor_scraper` 的所有参数都是可选的（`keyword: str = ""`），
所以传一个未知参数 `wrong_arg` 进去时，Python 的 `**kwargs` 展开机制
在 `TypeError` 触发前根本没机会报错 —— 函数签名对得上（因为都不传也行），
多了的字段被静默丢弃。

这类问题的危险在于：**调用方以为自己在传过滤条件，实际什么都没传**，
于是 Agent 拿到的是"全量数据"，推理结论失效，但整个链路不会报任何错。

### 修复

在调用前，用工具的 JSON Schema 做**预校验**（而不是事后靠 Python 报错）：

```python
# 1) 必填字段检查
missing = [k for k in spec.parameters.get("required", []) if k not in arguments]
if missing:
    return _fail(record, f"缺少必填参数: {missing}")

# 2) 未知字段检查（这正是之前漏掉的）
allowed_props = set(spec.parameters.get("properties", {}).keys())
unknown = [k for k in arguments if k not in allowed_props]
if unknown:
    return _fail(record, f"未知参数: {unknown}，允许的参数为: {sorted(allowed_props)}")
```

这一步还有个额外收益：**错误的报错信息可以直接回传给 LLM**，
让模型自我修正。这比抛一个 Python 堆栈有用得多。

### 实践意义

**Q: LLM 调用工具的可靠性怎么保证？**

> 三层防御：
> ① **Schema 预校验**：在进入函数体之前，用 JSON Schema 校验必填项和字段白名单。
> 这样错误信息是"人话"，能直接喂回给模型让它重试。
> ② **结构化输出**：要求模型返回严格 JSON，用 Pydantic 二次校验。
> ③ **错误反馈修复循环**：把校验失败信息拼进下一轮 prompt，
> 最多重试 N 次。这套在 `llm/client.py::chat_structured` 里实现了。
>
> 关键洞察：**工具调用失败的最佳处理方式不是抛异常，而是把错误变成可理解的反馈**。

## 坑 5 · mock 模式下评测通过率只有 40-60%（这不是 bug）

### 现象

`python scripts/run_eval.py` 在 mock 模式下跑，通过率 40%~60%，多个用例红。

### 根因分析

这是一个**"看起来像 bug，实际是正确行为"**的现象。

mock 模型的返回是固定占位文本（比如"这是一份由 mock 模型生成的报告"），
而评测用例断言里包含业务关键词命中率检查：

```python
assert all(kw in report for kw in ["库存", "周转", "补货"])
```

占位文本当然不含这些词 → 断言必然失败。

**关键判断**：如果 mock 模式下通过率是 100%，那才说明评测**坏了** ——
因为评测应该能识别出"内容质量不合格"，而不是只看"流程跑通了"。

### 处理

不动代码，而是**在文档里把这件事写清楚**（`docs/eval_report_README.md`）：

| 模式 | 期望通过率 | 说明 |
|---|---|---|
| mock | 40%~60% | 占位文本无法命中业务关键词，L1 断言必然部分失败。**这是评测在正常工作的证据** |
| 真实模型 | ≥85% | 真实生成内容才能通过质量断言 |

并在 README 里注明：**简历上写的评测数据必须用真实模型跑出来**，
不能用 mock 数据充数（"你用的什么模型跑的这个数"说不清楚就是自欺欺人）。

### 实践意义

**Q: 你怎么知道你的评测系统本身是可信的？**

> 我做了一个反向验证：故意让 mock 模型输出垃圾文本，
> 观察评测是否能识别出来。结果是能 —— 通过率掉到 40-60%。
> 这证明评测不是"橡皮图章"。
> 反过来，如果任何输入都 100% 通过，说明评测指标设计失效了，需要重新设计断言。

**Q: 评测体系怎么分层？**

> 四层（详见 `app/eval/harness.py`）：
> - **L1 确定性断言**：关键词命中、字段完整性、格式合法性 —— 快、准、零成本
> - **L2 Agent 行为指标**：子任务数、工具调用次数、重试次数、是否需要人工介入 —— 看"过程"而非"结果"
> - **L3 LLM-as-Judge**：让另一个模型按 rubric 打分 —— 覆盖语义质量
> - **L4 人工校准**：人工抽检并与 L3 打分对比 —— 校准 Judge 是否可信
>
> 分层原则：**能用确定性规则判的绝不用模型判**，模型判的必须有抽检兜底。

## 坑 6 · 长任务产物只存内存，服务一停全部丢失（最"贵"的坑）

### 现象

用真实模型跑完一个 11.6 分钟、57,958 token、1.3 万字的完整运营报告，
想把它导出给用户时发现：**内容取不回来了**。

排查过程：

```
1. 查 TaskStore  → 内存 dict，进程一停就没了
2. 找 SQLite 库  → data/*.db 不存在（生产从未接库）
3. 查 trace 文件 → tr_094845f0d766.json 里只有「指标」：
                   trace_id / task_id / total_tokens / total_cost_usd / spans
                   —— 没有任何一段交付物正文
4. 结论          → 这份报告永久丢失，约 ¥0.13 的成本 + 12 分钟白花
```

### 根因

两个设计缺陷叠加：

**缺陷 1：`TaskStore` 是纯内存 `dict`**

```python
# 问题代码
class TaskStore:
    def __init__(self) -> None:
        self._tasks: dict[str, dict[str, Any]] = {}   # ← 进程内，重启即归零
```

**缺陷 2：把「指标」和「产物」混为一谈**

trace 记录的是**可观测性数据**（token、耗时、成本、span 树），
它的设计目标是**性能分析**，不是**产物存储**。
`finalize` 节点算出了 1.3 万字正文，却只把它塞回内存 state——
而 state 的生命周期 = 进程生命周期。

> **共性认知**：内存态只适合做**缓存**，永远不能做**唯一存储**。
> "长任务 + 长驻进程"是这个问题的高发组合：
> 任务跑得越久、越贵，丢失时的损失越大，但恰恰长任务最可能跨重启。

### 修复

**修复 1：`TaskStore` 落盘（持久化）**

```python
class TaskStore:
    def __init__(self, persist_dir: Path | None = None) -> None:
        self._tasks: dict[str, dict[str, Any]] = {}
        self._dir = persist_dir or (settings.data_dir / "tasks")
        self._dir.mkdir(parents=True, exist_ok=True)
        self._load_from_disk()          # 启动即恢复历史任务

    def _path(self, task_id: str) -> Path:
        # task_id 来自外部输入，必须净化，防路径穿越
        safe = "".join(c for c in task_id if c.isalnum() or c in "-_")
        return self._dir / f"{safe}.json"

    def save(self, task_id: str, data: dict[str, Any]) -> None:
        payload = json.loads(json.dumps(data, ensure_ascii=False, default=str))
        payload["task_id"] = task_id
        self._tasks[task_id] = payload
        try:                             # 落盘失败也不影响主流程（降级为纯内存）
            self._path(task_id).write_text(
                json.dumps(payload, ensure_ascii=False, indent=2), encoding="utf-8")
        except Exception as exc:
            logger.warning("任务落盘失败 %s: %s", task_id, exc)
```

**修复 2：`finalize` 节点归档交付物（产物可追溯）**

```python
# 内容落 Markdown（可读、可 diff、可直接交付业务方）
out_dir = settings.data_dir / "deliverables"
md_path = out_dir / f"{safe_id}.md"
head = (f"<!-- task_id: {state['task_id']} -->\n"
        f"<!-- goal: {plan.goal or state['query']} -->\n"
        f"<!-- score: {critique.score if critique else 'N/A'} -->\n"
        f"<!-- rounds: {state.get('revision_round', 0)} -->\n\n")
md_path.write_text(head + final_content, encoding="utf-8")
```

**修复 3：新增下载接口 `GET /api/task/{id}/deliverable`**

让产物能被程序化取回，而不是只能"人肉去服务器翻文件"。

### 验证

跑了一个专门的验收任务（trace `tr_acb6eb6301c5`）：

| 验收项 | 结果 |
|---|---|
| 归档文件 | ✅ `data/deliverables/task_e2everify.md`（3,657 字正文）|
| 元信息头 | ✅ 含 task_id / goal / score / rounds |
| 任务 JSON `archived_path` | ✅ 已写入 |
| 下载接口 | ✅ 返回完整 Markdown |

并补了 2 个回归测试（`TestDeliverableArchival`）：
- `test_finalize_archives_markdown`：交付物必须真实落盘且含元信息头
- `test_archive_path_is_sanitized`：`../../evil` 这类 task_id 不得穿越目录

### 实践意义

**Q: Agent 长任务（几十分钟）跑完了，结果丢了，你怎么排查和防止？**

> 先分层看"结果存在哪"。一般有三个地方：① 执行引擎的 state/checkpoint（为了恢复执行）
> ② 面向业务的查询视图（为了给前端展示）③ 可观测性 trace（为了性能分析）。
> **这三个都不是"产物存储"**。
>
> 我实际的坑就是：1.3 万字报告只存在于执行 state 里，而 state 是内存态；
> trace 里只有 token/耗时这些指标，没有正文。服务一停就全没了。
>
> 修复是两条：一是让业务视图（TaskStore）落盘，
> 二是让 finalize 节点把产物**主动归档**成 Markdown 并记录路径。
> 另外补了路径穿越防护和回归测试——因为 task_id 是外部输入。
>
> 根本原则：**内存只能做缓存，不能做唯一存储；指标和产物必须分开归档。**

**Q: 为什么不直接存数据库，而要落 JSON 文件？**

> 演示环境零依赖优先（开箱即跑、CI 不被迫装 PG）。
> 但关键不是"用文件还是用库"，而是**读写都收敛在 `TaskStore` 一个类里** ——
> 换 PostgreSQL / S3 只需改这一个类，调用方零改动，这是依赖倒置的价值。

## 总结：这 6 个坑的共性

| 坑 | 本质 | 通用教训 |
|---|---|---|
| 1 · 序列化崩溃 | 状态分层不清 | 可持久化状态 ≠ 运行时副作用，必须物理隔离 |
| 2 · 安全静默失效 | 依赖默认值 | 失败必须显式声明，不能靠"忘记改默认值" |
| 3 · 无谓重试 | 异常分类粗糙 | 重试的前提是"失败可恢复" |
| 4 · 参数静默丢弃 | 校验时机错位 | 在边界做校验，且错误信息要能回喂给 LLM |
| 5 · 评测低通过率 | 判据被误读 | 先证明度量工具本身可信，再谈度量结果 |
| 6 · 长任务产物丢失 | 指标与产物混存 | 内存只做缓存；产物必须主动归档、可追溯 |

一句话概括：**它们的共性都是"错误没有被正确表达"** ——
要么被默认值掩盖，要么被当成可重试，要么被静默丢弃，要么被误判为故障。

> **怎么用这份文档**：把它当成工程决策的记录，而不是流水账。
> 当被问到"你遇到过什么困难"时，挑坑 2（静默失败）或坑 1（状态分层），
> 按 `现象 → 根因 → 修复 → 架构层面的反思` 讲，比讲"我实现了某某功能"更有说服力。
