## 二、Run 1 vs Run 2 观测差异（描述性，非因果）

两次任务相同：**「分析厨房收纳品类竞品定价」**

| 指标 | Run 1 | Run 2 | 观测差异 |
|---|---|---|---|
| 质量评分 | 0.72 | 0.916 | +0.196 |
| 墙钟耗时 | 1,396.7 s | 698.4 s | −50% |
| 总 token | 130,159 | 57,958 | −55% |
| 反思轮次 | 2 | 1 | −1 |
| 超时重试 | 有（同请求重复请求）| 0 | 归零 |

> ⚠️ **为什么不把"−50%"写成流式改造的功劳？**
> 两次运行的**反思轮次不同**（2 轮 vs 1 轮），而 1 轮 revise 本身就占 ~350s / ~2.5万 token。
> 仅"少改一轮"就足以解释大部分差异。这是一个**混杂因素（confounder）**。
> 要证明流式改造的净收益，需要"同为 1 轮反思、仅切换流式/非流式"的对照实验——本项目未做。

**已确证的机制（讲机制，不讲提升率）：**

非流式调用下，`httpx` 的 timeout 约束的是**首字节到完整响应的总时长**；
Writer 生成长文时极易超时，从而触发重试。流式下 read timeout 约束的是
「**两个 chunk 之间的最大间隔**」——只要模型持续吐字就不会超时。
Run 2 的单次长文生成（`writer:revise`，23,443 输出 token）未发生重试，与此机制一致。

## 四、关键性能洞察（面试可讲的三点）

### 洞察 1 · 反思循环是最大成本黑洞

在 Run 2 里，`writer:revise` 一个节点吃掉 **51% 的成本、52% 的时间**
（$0.009032 / $0.017697；363.5s / 698.4s，均为该 trace 内实测占比）。
所以必须设**轮次上限** + **「越改越差回滚」**——无限自我批判会把成本烧穿。

### 洞察 2 · 反思轮次是最敏感的成本杠杆

对比 Run 1（2 轮）与 Run 2（1 轮）：**1 轮 revise 本身就占 ~350s、~2.5 万 token**。
这说明"多打回一轮"的代价极大，**Critic 通过阈值是最该用数据调的参数**，
而不是拍脑袋定。（注：这是单次观测，不是受控实验，只用于说明量级。）

### 洞察 3 · 长文生成必须用流式

**机制层面（已确证）**：
- 非流式下 `httpx` timeout = 首字节到完整响应的**总时长** → 长文极易被掐断并触发重试
- 流式下 read timeout = **两个 chunk 之间的最大间隔** → 只要持续吐字就不超时

**观测证据**：Run 2 的单次长文生成（`writer:revise`，输出 23,443 token）**零重试**完成。
设计 timeout 必须区分「总时长」与「chunk 间隔」两种语义，否则要么误杀正常长文，
要么把重试成本放大到不可接受。

## 八、简历引用建议

**可直接引用的实测事实（数字均可回溯到 trace）：**

> - 基于 LangGraph 编排 6 角色 Agent，自动完成"市场调研 → 竞品分析 → Listing →
>   广告词 → 评论洞察 → 周报"全链路
> - 三次真实运行的全部指标（耗时 / token / 成本）均落盘在 `data/traces/`，
>   可用 `python -m app.eval.metrics_report` 一键复算（避免手写数字）
> - 落地交付物自动归档机制，长任务产物可追溯、可通过 API 取回

**面试时主动说的限制（诚实是加分项）：**

> - 工具是**确定性模拟实现**（保证可复现、零外部依赖）；生产需替换 handler
> - Checkpointer 默认内存态；生产切 PostgreSQL 只需改配置（降级逻辑已实现，依赖为可选）
> - 未引入 Redis / Celery 等外部中间件；缓存用进程内实现，生产可替换（接口已收敛在 ToolRegistry）
> - 内置评测集 **20 条**（覆盖 6 类场景），是"种子集"而非生产级规模
> - **未做"改造前 vs 改造后"的严格 A/B 对照统计**，因此本档案不宣称任何"提升率"
