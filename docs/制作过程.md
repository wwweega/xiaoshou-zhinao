## 一、背景与目标

### 1.1 问题从哪来

跨境电商运营是个**高度重复、且强依赖多环节协作**的活儿：市场调研 → 竞品分析 → 评论洞察 →
Listing 生成 → 广告关键词 → 运营周报。传统做法里，这些环节要么靠人手动查数据、写文案，
要么靠零散的脚本拼接，**没有一个能"接一个需求、自动跑完全流程"的系统**。

单靠一个"大模型 + 一段 prompt"也解决不了，因为：

- 运营任务**天然是多步的**（先调研再分析再写文案），单轮 prompt 撑不住；
- 任务**需要工具**（查数据、算指标、抓竞品），纯对话模型拿不到实时数据；
- 企业最怕的是"**不可控**"——过程黑盒、结果没法验收、出错没法定位。

### 1.2 目标（可验收）

所以定的目标是：用 **LangGraph 把 6 个角色 Agent 编成一张状态图**，
自动完成跨境电商运营全流程，且满足三条硬标准：

| 目标 | 可验收的表现 |
|---|---|
| 可控 | 流程是显式状态图，每一步可干预、可回滚 |
| 可度量 | 全链路 Trace 树 + 成本记账 + 三层评测 + CI 门禁 |
| 可复现 | 工具确定性模拟、无外部依赖也能跑通（mock 基线） |

一句话：**核心不是"能跑通"，而是"可控 + 可度量"——这是企业级 AI 应用和 Demo 的分界线。**

## 二、技术选型：每个选择都是一次取舍

### 2.1 为什么用 LangGraph，而不是自己写编排 / 用纯 Agent 框架

| 方案 | 优点 | 为什么没选 / 怎么选 |
|---|---|---|
| 自己写 while 循环编排 | 无依赖、可控 | 状态管理、断点续跑、条件边都要手写，**重造轮子且易错** |
| 纯 ReAct Agent（一次想一步） | 灵活 | 步骤不可预期，**无法保证流程完整性**，企业不敢用 |
| **LangGraph 状态图** ✅ | 显式图、支持条件边/循环/Checkpointer | 流程**显式可读**，能插断点、能观测、能回滚 |

**核心取舍**：企业场景要的是**流程确定性**，不是"Agent 自由发挥"。
LangGraph 的显式状态图正好把"多步协作"变成"一张可读可测的图"。

### 2.2 为什么是"6 个角色 Agent"而不是"1 个全能 Agent"

单一巨型 prompt 的问题：**职责不清、互相干扰、无法独立评测**。
拆成 6 个角色（prepare / planner / researcher / analyst / writer / critic）后：

- 每个 Agent 的输入输出是**清晰的契约**（Pydantic schema），可单测；
- planner 输出的是 **DAG（子任务有依赖关系）**，execute 按拓扑序分批并行；
- critic 独立审核 + revise 回灌重写，形成**闭环质量保障**。

### 2.3 为什么工具要"确定性模拟"

真实工具（抓竞品、查汇率、连 ERP）依赖外部服务和凭证，
会让 **CI 跑不起来、复现困难、结果不稳定**。

**决策**：工具用**确定性模拟实现**（同样的输入给同样的输出），保证零外部依赖、CI 可跑、结果可复现。
生产替换只需改 handler，**Agent 侧代码零改动**——这是**依赖倒置**的价值。

### 2.4 存储与模型

| 组件 | 选择 | 理由 | 降级 |
|---|---|---|---|
| 编排 | LangGraph | 显式状态图 | — |
| 存储 | SQLite | 零运维、够用 | 可换 PG |
| 缓存 | 进程内 LRU | 单机开发够用 | 可换 Redis |
| 模型 | 百炼（DeepSeek/通义/智谱/OpenAI 兼容） | 国内可直连 | mock 模式 |

**共同原则**：默认存储 SQLite、缓存进程内 LRU，**不强制依赖 PG/Redis**，让读者 `pip install` 就能跑。

## 三、核心难点与解决方案

> 以下都是开发过程中**真实遇到并修复**的。完整版（现象→根因→修复→面试价值）见 [`踩坑记录.md`](踩坑记录.md)。

### 难点 1：运行时观测对象塞进 state，导致序列化崩溃

**现象**：工作流跑到第二个节点就崩，报 `Type is not msgpack serializable: TraceRecorder`，
报错点不在业务代码，而在 LangGraph 内部。

**根因**：把 `TraceRecorder`（含 `threading.Lock` 等运行时对象）直接放进了 `GraphState`。
而 LangGraph 的 Checkpointer 会在每个 super-step 后**序列化整个 state**（msgpack），运行时对象无法序列化。
本质是**职责混淆**：state 是"可持久化的业务事实"，追踪器是"进程内的观测副作用"。

**解法**：用标准库 `contextvars` 承载追踪器——它在 asyncio 中**每个 Task 独立上下文**，
并发不串扰，嵌套 Agent 调用也能读到；用完必须 `reset`，否则污染事件循环。

**面试价值**：能讲清"什么该进 state、什么绝不能进"，是工程成熟度的信号。

---

### 难点 2：墙钟延迟算错，偏差 3.7 倍

**现象**：端到端延迟统计出来**只有真实值的 1/4 左右**。

**根因**：最早用 `max(单个 span 的 latency)` 当端到端耗时。但图里的节点是**顺序执行**的，
最长的单个节点绝不等于整条链路的耗时。

**解法**：端到端墙钟 = **所有 span 时间区间的并集** = `max(end_ts) - min(start_ts)`。
（这个坑后来在「知枢」项目里以**升级版**再现：阶段耗时对嵌套 span 重复求和，
一度出现"阶段耗时 > 端到端"的物理不可能结果——根因同源，都是**没做区间运算**。）

**面试价值**：时间统计必须用**区间运算**，不能用简单加减——这是可观测性的基本功。

---

### 难点 3：`sql_query` 工具的"安全四道闸"

**现象**：让 Agent 有查数据库的能力，但**裸奔的 SQL 工具是生产事故的温床**
（注入、全表扫描、误删）。

**解法**：`sql_query` 设四道闸——
① **只读校验**（拒绝 INSERT/UPDATE/DELETE/DROP 等）；
② **表白名单**；③ **返回行数上限**；④ **查询超时**。

同理 `calculator` 工具**不用 `eval`**，而是走 **AST 白名单**，杜绝代码注入。

**面试价值**：给 Agent 接工具时，"**能力边界**"和"**安全边界**"必须同时设计。

---

### 难点 4：越改越差 —— critic/revise 循环需要"回滚"

**现象**：critic 打回 → revise 重写 → 有时**改得比原来还差**，但流程还会继续。

**解法**：在 finalize 阶段做**自动回滚**——若修订版评分低于历史最佳，则回退到最佳版本，
并把"这次修订为什么失败"写入长期记忆，避免重复犯错。

**面试价值**：多 Agent 反思循环不是"转起来就行"，**必须有收敛保证和回滚兜底**，
否则会陷入"越改越烂"。

---

### 难点 5：模型路由与结构化输出修复

**现象**：不同任务对模型要求不同（规划要强推理、摘要要快且便宜）；
且模型偶尔不按 JSON schema 输出，导致解析失败。

**解法**：
- **模型路由**：按任务类型选模型（强模型做 planner，小模型做摘要），控成本；
- **结构化输出修复**：解析失败时先尝试"提取 JSON 子串 / 去代码围栏"，仍失败才重试，
  重试仍失败则**判定失败而不是硬编造**。

**面试价值**：生产级 LLM 应用，"结构不稳"是常态，**必须有修复 + 兜底策略**。

## 四、验证方式：怎么保证"真的对"

1. **单元测试（46 个）**：全链路走降级/确定性实现，`pip install` 后即可跑；
2. **三层评测**：单元级（工具正确性）→ 集成级（流程完整性）→ 端到端级（任务质量）；
3. **CI 门禁**：指标不达标退出码非 0，拒绝合并；
4. **真实模型实测**：用百炼真实跑，归档 Trace 与成本（见 [`真实模型实测报告.md`](真实模型实测报告.md)、[`实测数据档案_三次真实运行.md`](实测数据档案_三次真实运行.md)）。

## 五、局限与后续

**当前局限（诚实说明）**：
- 工具体是**确定性模拟**，接真实数据源是下一步；
- 评测以功能与流程为主，任务质量的统计基准仍需扩样本；
- 未做鉴权/多租户，聚焦 Multi-Agent 编排本身。

**若继续做**：接真实数据源 → 扩评测样本 → 引入 A/B 与人工评分校准 → 多租户。

---

## 六、一句话总结

> 这个项目最花时间的不是"把 6 个 Agent 串起来"，而是**让这个系统"可控、可度量、可复现"**——
> 显式的状态图、统一的 Trace、确定性的工具、按单项下限卡的评测门禁。
> **企业级 AI 应用和 Demo 的分界线，从来不是"能不能跑"，而是"出事时你能不能说得清、兜得住"。**
