# 运营智脑 · 面试题手册

> 这个项目的每一行代码都是面试题。下面按模块整理了 40 个高频问题，
> 每个问题都给了「直接可背的回答框架」。**背框架，不背逐字稿**——
> 面试官一追问细节，逐字稿就露馅。

---

## 一、项目整体与选型（必问，开口前 3 分钟决定印象）

### Q1 用一句话介绍这个项目
> 「运营智脑是一个跨境电商运营自动化平台。它用 LangGraph 把 6 个角色 Agent
> 编成一张状态图，自动完成从市场调研、竞品分析、Listing 生成到运营周报的全流程。
> 我把重点放在了两件应届生项目通常不做的事上：**一是可控性**——
> Critic 独立评审 + 回灌重跑 + 越改越差自动回滚；**二是可度量**——
> 一套覆盖确定性断言、Agent 行为指标和 LLM 裁判的三层评测体系，能进 CI 做回归门禁。」

**注意**：一定要在介绍里埋下"可控性"和"可度量"两个钩子，这两个词会让面试官追问，
而追问的方向恰好是你准备最充分的地方。

### Q2 为什么选跨境电商这个场景？
三个理由，按重要性排：
1. **业务链条完整**：调研→分析→创作→审核，天然适合多 Agent 分工，能展示编排能力
2. **有客观评测标准**：合规红线（绝对化用语、医疗功效）是可确定性判断的，
   不像闲聊类应用无法评测
3. **厦门本地产业**：跨境电商是厦门 AI 岗最密集的用人场景，我做的时候特意调研过 JD

### Q3 为什么用 LangGraph 而不是自己写 while 循环？
| 维度 | 自己写循环 | LangGraph |
|---|---|---|
| 并行执行 | 手写 asyncio 编排，容易出竞态 | super-step 天然并行，reducer 保证状态合并正确 |
| 断点续跑 | 要自己设计状态快照 | Checkpointer 内置，传 thread_id 即可恢复 |
| 可观测 | 自己埋点，容易漏 | 每个节点天然是独立 span |
| 可维护 | 流程藏在代码里，新人要读半小时 | 图结构可导出 Mermaid，一眼看懂 |

**加分说法**：「如果只是 3 个节点的直线流程，我会用 while 循环，不值得引入框架。
但我的流程有两条循环边（批次推进 + 反思回灌）和并行分支，
这种图结构用框架的价值才显现出来。」——这句话证明你会做技术选型判断，不是无脑堆技术。

### Q4 为什么不用 AutoGen / CrewAI？
- CrewAI：抽象层次高，但流程控制藏在框架内部，我想精确控制"何时打回重跑"反而别扭
- AutoGen：偏对话式协作，适合开放式讨论，我的场景是明确的 DAG，不需要自由对话
- LangGraph：把编排权交给我，循环边、条件边、状态 schema 都是显式的

**关键**：说清"我评估过、我知道取舍"，比说"这个最火"强 10 倍。

## 二、Multi-Agent 协作机制（技术深水区）

### Q5 Multi-Agent 比单 Agent 到底强在哪？ 
**四个点，每个都要能展开讲：**

1. **认知负载分离**：一个 prompt 里同时要求"分析数据 + 写文案 + 自我检查"，
   模型会顾此失彼。拆开后每个 prompt 只专注一件事，质量明显更高。
2. **上下文隔离（这条最重要）**：Researcher 消化几万字的原始工具数据，
   只把 200 字结论交给 Analyst。每一跳都做了信息压缩。
   如果全塞一个 Agent，prompt 里会堆满原始数据，注意力被稀释
   （lost in the middle 现象），成本还高。
3. **可独立评测**：Critic 能给出「事实性 0.7 / 可读性 0.9」这类分维度分数，
   我立刻知道该改哪个 Agent 的 prompt。单 Agent 只有一个总分，无从下手。
4. **权限最小化**：Researcher 只能用采集类工具，Writer 只能用生成类工具，
   从架构上避免了"写文案的 Agent 突然去查数据库"这种越权。

### Q6 Multi-Agent 的代价是什么？
**敢主动说缺点，是专业度的强信号。**

1. **延迟叠加**：每多一跳就多一次 LLM 调用，端到端延迟变长
2. **成本叠加**：6 个 Agent 意味着至少 6 次 LLM 调用
3. **误差累积**：上游错了，下游会放大（Researcher 抓错数据 → Analyst 算出错误结论 →
   Writer 写出错误文案）
4. **调试困难**：跨 Agent 的问题定位比单 Agent 难

**我的对策**：①模型路由把简单任务的成本压下去（60% 的子任务走小模型）
②Critic 独立校验做误差拦截 ③全链路 Trace 让跨 Agent 问题能定位到具体一跳。

### Q7 什么时候不该用 Multi-Agent？
> 「任务能用一次 LLM 调用解决的，绝不拆成多 Agent。
> 简单任务拆多 Agent 是负优化——延迟翻几倍，质量却没有提升，还多了一堆故障点。
> 我的判断标准是：如果这个任务需要**多种不同性质的认知工作**
> （取数 vs 推理 vs 创作 vs 审核），才值得拆。」

**这句回答是分水岭**，能说出来的候选人不到 10%。

### Q8 Agent 之间怎么通信？为什么用共享状态而不是直接传消息？
我用的是 **黑板模式（Blackboard）** + LangGraph State：
- 所有 Agent 读写同一个 `GraphState`，谁需要什么自己取
- 好处：新加一个 Agent 不用改其他 Agent 的接口，只要声明依赖哪个字段
- 代价：状态膨胀风险（要控制写入字段），所以我对 `subtask_results` 做了
  截断（单条 1200 字）和按依赖注入

**对比**：如果直接消息传递（A 调 B、B 调 C），耦合度高，
加一个 Cross-Check Agent 就要改整条链路。

## 三、状态图与编排（LangGraph 深挖）

### Q9 什么是 super-step？为什么这个概念重要？
一个 super-step = 图中所有「当前可执行节点」并发跑一轮 + 状态合并，然后进入下一轮。
这是 Pregel 风格的 BSP（Bulk Synchronous Parallel）计算模型。

**为什么重要**：它决定了并行的粒度。我在 `execute` 节点里一次跑一批子任务，
这一批就是同一个 super-step 内并发执行的。

### Q10 reducer 是干什么的？不用会怎样？
reducer 定义「同一个字段被多个节点同时更新时怎么合并」。

**不用会怎样**：LangGraph 默认后写覆盖。并行 super-step 里两个节点同时往
`subtask_results` 写，就会丢数据。**这是偶发 bug**——
单条测试跑 10 次可能都对，并发压测必炸。我踩过这个坑，所以专门给
`subtask_results` 和 `events` 定义了合并函数。

### Q11 条件边怎么实现循环？怎么防止死循环？
两条条件边：
- `route_after_execute`：还有可执行子任务 → 回 execute；否则 → writer
- `route_after_critic`：不通过且轮次 < max_reflection_rounds → revise；否则 → finalize

**防死循环三重保险**：
1. 轮次硬上限（配置化，默认 2）
2. token 预算上限
3. 越改越差自动回滚（如果修订后评分下降，用回滚版本）

### Q12 断点续跑怎么做到？
1. 编译图时传入 checkpointer
2. 每次 invoke 带 `config={"configurable": {"thread_id": "..."}}`
3. 每个 super-step 结束后自动持久化状态
4. 恢复时用同一个 thread_id 再 invoke，框架从最后 checkpoint 继续

**容易答错的点**：不是"有 thread_id 就能续跑"。还要满足
①状态可序列化 ②图结构没变（改了图结构旧 checkpoint 可能不兼容，生产中要版本化图）。
这个细节说出来，面试官会认为你真跑过。

### Q13 任务级并行和节点级并行有什么区别？
这是两层不同粒度的编排，**很多人混为一谈**：
- **节点级**（LangGraph 管）：决定 prepare → planner → execute 怎么走
- **任务级**（我自己的 DAG 调度器管）：决定一个 execute 节点内部，
  多个子任务谁先谁后、谁能并发

我用 `next_ready_subtasks()` 做拓扑排序，把 DAG 切成批次。
t1、t2 无依赖就同批并发，t3 依赖它俩就下一批。

## 四、工具调用（MCP / Function Calling）

### Q14 怎么让模型正确调用工具？
三个要素，**缺一个都会导致出错率上升**：
1. **描述要写"什么时候用"**，不只是"是什么"。
   例：不要写「查询库存」，要写「查询 SKU 的实时库存、在途量与可售天数，
   返回补货预警。用于运营周报与补货决策」
2. **参数 schema 要有描述和默认值**，降低模型瞎猜的概率
3. **错误要回灌**：工具失败时把报错原文返回给模型，让它自己改参数重试

> 面试提示：如果你实际做过 A/B 对比（开关第 3 点分别跑），就给出你测到的数字；
> 没做过就**只讲机制**，不要说"我从 X 提升到了 Y"。编造提升率是最容易被追问穿帮的
> ——面试官会问"样本多少、怎么判定对错、置信区间多少"。

### Q15 工具调用失败怎么处理？
分三类，**处理方式完全不同**（这个分类是加分项）：
| 失败类型 | 是否重试 | 处理方式 |
|---|---|---|
| 超时 / 429 限流 | ✅ 重试 | 指数退避 + 抖动，最多 2 次 |
| 参数错误 | ❌ 不重试 | 立即失败，把 schema 和错误回灌给模型重新决策 |
| 权限拦截（如 DROP TABLE） | ❌ 不重试 | 直接拒绝并告知安全策略 |

**为什么参数错误不重试**：参数错了重试还是错的，只会浪费时间和 token。
正确做法是让模型重新想参数。

### Q16 为什么所有工具必须走同一个调用入口？
只有收口，才能统一做这几件事：
- Trace（每个工具调用的耗时与状态）
- 超时控制
- 重试与退避
- 幂等缓存
- 参数校验
- 指标统计（tool_error_rate）

如果每个 Agent 直接调 handler，这些能力要写 12 遍，而且必然漏掉几个。

### Q17 幂等缓存怎么做？为什么需要？
用 `工具名 + 幂等键 + 参数哈希` 做 key 缓存结果。
需要它的原因：①Agent 可能重复调用同一工具（模型决策不稳定）
②重试时不该重复扣费 ③同一批次里多个子任务可能查同样的数据。

**并发下要防缓存击穿**：用 per-key 的 asyncio.Lock，
保证同一 key 并发时只有一次真实调用。

### Q18 模型生成的 SQL 直接执行安全吗？
**绝对不安全**。必须四道闸：
1. 只读校验（禁 drop/delete/update/insert/alter/truncate）
2. 表白名单
3. 行数上限（LIMIT）
4. 超时控制

我在代码里做了关键词拦截 + 白名单校验。
**生产还要加**：独立只读账号、查询审计日志、SQL 解析器级校验（比关键词匹配更可靠）。

## 五、记忆与上下文工程（区分度最高）

### Q19 为什么不能让 Agent 记住全部历史？
**O(n²) 成本问题**：第 20 轮的 prompt 包含前 19 轮全部内容，
token 消耗随轮次平方增长。而且长上下文会稀释注意力（lost in the middle），
模型反而抓不住重点。

### Q20 你的记忆系统怎么设计的？
三层：
- **L1 短期缓冲**：最近 6 条原文保留 → 保证指代消解（"它""那个产品"能对上）
- **L2 摘要记忆**：超出窗口的历史压缩成**结构化**摘要
  （目标 / 已确认事实 / 关键数字 / 未决问题）→ 省 token 但关键信息不丢
- **L3 长期记忆**：历史任务结论向量化存储，按语义相关性召回 → 跨任务复用

### Q21 为什么摘要要结构化，不让模型随便总结？
自由总结会丢掉关键实体——品牌名、具体数字、结论。
我用固定模板（目标/事实/数字/未决问题）约束，实测关键信息保留率明显更高。
**这是个很容易被追问的点**：面试官会问"你怎么验证摘要没丢信息"，
答案就是"结构化字段化，可以逐项检查"。

### Q22 上下文工程具体在做什么？
三件事：
1. **保住指代消解必需的原样对话**（短期窗口）
2. **把远期历史压成摘要**（压缩）
3. **不让无关内容占据注意力预算**（筛选）

我的具体做法：只注入 `depends_on` 声明的上游子任务产出，
单条截断 1200 字。**这就是"依赖驱动的最小上下文"**，
也是我 token 成本下降的主要来源之一。

### Q23 为什么长期记忆要"双写"（向量库 + 事实表）？
向量检索擅长模糊语义，但不擅长精确查询（"查 SKU-1001 上次的结论"）。
所以生产上是：
- 向量库做**召回**（语义相似）
- 结构化表做**精确查询**（键值命中）

这跟 RAG 里「向量检索 + BM25 混合检索」是同一个思路。

### Q24 长期记忆的相似度阈值怎么定？
必须设阈值（我用 >0.05）。不设的话永远能召回 Top-K，哪怕全是垃圾，
会污染上下文。**更高阶的做法**：用人工标注的"该不该召回"样本对，
画 P-R 曲线选阈值——这是数据驱动的做法，能说出来很加分。

## 六、模型路由与成本优化（老板最关心）

### Q25 你怎么把成本降下来的？
三个杠杆，**按贡献排序**：
1. **模型路由**（贡献最大）：按任务复杂度打分，<0.5 走小模型。
   抽取、分类、意图识别这类"机械劳动"小模型完全够用，成本差 3-4 倍。
   我的数据是约 60% 的调用路由到了小模型。
2. **上下文压缩**：只注入依赖项 + 截断 + 摘要，token 消耗显著下降
3. **幂等缓存**：相同参数的重复调用直接命中缓存

### Q26 复杂度打分怎么设计的？为什么这么设计？
四因子加权，**关键是可解释**：
- 角色基础权重（planner 0.75 / writer 0.80 / researcher 0.40）
- 描述长度因子（最多 +0.1）
- 推理关键词命中（"策略/优化/分析/对比/建议/预测/洞察"，每个 +0.05，上限 +0.2）
- 阈值 0.5 作为冷启动分界线

**为什么不用分类器**：冷启动阶段没有标注数据。
先用规则上线，收集真实的"小模型失败案例"作为标注数据，
再训练分类器替换——这是标准的工程演进路径。

### Q27 阈值 0.5 怎么定？拍脑袋吗？
**诚实回答 + 给演进路径**：
「0.5 是冷启动拍的，因为要先把系统跑起来。
真正该做的是：统计小模型在各任务类型上的失败率，
失败率超过 15% 的类型就调高阈值交给大模型。
这是数据驱动的调参，我把它列为下一步优化项。」

### Q28 怎么防止成本失控？
三层预算：
1. 单任务 token 预算（80000）
2. 反思轮次上限（2 轮）
3. 工具重试上限（2 次）

**核心思路**：一切循环都必须有预算上限。
没有上限的 AI 循环理论上可以烧光你的余额。

## 七、质量与评测（最值钱的一节）

### Q29 你怎么知道系统"效果好不好"？
**这是我认为这个项目最有价值的地方。** 我建了三层评测：

| 层级 | 内容 | 特点 |
|---|---|---|
| L1 确定性断言 | 非空、长度、关键词命中、违禁词、结构完整 | 快、免费、100% 稳定，能进 CI |
| L2 Agent 行为指标 | 子任务完成率、角色覆盖、依赖合法性、反思有效性、token 成本 | 针对 Agent 系统特有，可解释 |
| L3 LLM-as-Judge | 分维度质量打分（相关性/事实性/完整性/可执行性） | 有偏差，只用于抽样 |

**为什么以 L1/L2 为主**：它们便宜稳定可进 CI。
上来就全靠 LLM 打分是不可持续的评测体系（又慢又贵还不稳定）。

### Q30 LLM 当裁判有什么问题？你怎么缓解？
**问题**（能说出三个就够专业）：
1. 位置偏差：偏爱排在前面或更长的答案
2. 自我偏好：偏爱和自己风格相近的输出 —— 所以**同模型自评不可靠**
3. 分数通胀：倾向给 8/10，区分度低

**缓解手段**：
1. 拆成多维度分别打分，而不是打一个总分
2. 给评分锚点（0.6/0.8/0.9 分别对应什么）
3. 高风险项用确定性规则兜底，不完全信任 judge
4. **人工抽样校准**：抽 20-50 条人工打分，算和 judge 的 MAE，
   低于 0.1 才认为 judge 可用

**第 4 点是分水岭**——说不出这一步，说明你只是"用了 LLM 打分"，
而不是"建立了评测体系"。

### Q31 测试集怎么设计才不是"自己考自己"？
- 覆盖三类场景：**典型**（高频需求）+ **边界**（模糊、口语化、关键词堆砌）
  + **高风险**（合规红线，一票否决）
- 高风险用例单独标 critical
- **保留 holdout**：一部分用例调优时不许看，只在最终验收时跑，防止过拟合

### Q32 评测怎么进 CI？
`python -m scripts.run_eval` 在 CI 里跑，门禁规则：
- 所有 critical 用例必须通过
- 整体通过率 ≥ 80%

不通过就 block merge。**为什么必须进 CI**：
AI 应用最大的风险是**静默退化**——改一句 prompt，
90% 的 case 还正常，某一类场景悄悄崩了，上线后才发现。
回归门禁是唯一能拦住这个的机制。

## 八、并发与性能

### Q33 并发在哪里做的？怎么控制并发度？
两处并发：
1. **同批次子任务并发**：`asyncio.gather`
2. **同一子任务内多个工具调用并发**：`asyncio.gather`

**控制并发度的原因**：外部 API 有限流（RPM/TPM），
无限并发会把自己打死（全都 429）。
生产用 `asyncio.Semaphore` 做全局限流。

### Q34 asyncio.gather 要注意什么？
- `return_exceptions=True`：单个失败不能拖垮整批
- 并发任务之间**不能有共享可变状态**，否则要加锁
- 超时要单独设置（`asyncio.wait_for`），gather 本身不设超时
- 有语义依赖的调用**绝不能并发**（比如"先搜 ID 再查价格"）

### Q35 为什么用 SSE 不用 WebSocket？
- Agent 任务是**单向推送**（服务端推进度给客户端），不需要双向通信
- SSE 基于 HTTP，无需协议升级，**能穿透大多数企业网关**（WebSocket 常被防火墙拦）
- 自动重连机制（浏览器内置）
- 实现简单，服务端就是个 async generator

**什么时候该用 WebSocket**：需要客户端高频上行（比如用户实时打断、协作编辑）。

### Q36 SSE 的坑有哪些？
**能答出这些说明你真做过**：
1. **Nginx 缓冲**：必须加 `X-Accel-Buffering: no`，否则事件被攒着不发
2. **代理超时**：网关 read timeout 要大于任务时长
3. **客户端断连检测**：要能感知并取消任务，否则白烧 token
   （我用 `asyncio.CancelledError` 捕获）
4. **心跳保活**：中间长时间无事件会被中间设备掐断，定期发 `: heartbeat\n\n`
5. **格式严格**：`data: xxx\n\n` 两个换行，写错前端收不到

### Q37 长任务为什么要用任务队列？
- HTTP 连接不该占用几分钟（占着连接 = 浪费并发额度）
- 任务要能重试/重放
- 要能横向扩展 worker

我的做法：提供两条路径——小任务同步返回（便于演示），
长任务走后台 + 轮询/SSE 订阅。

## 九、可观测与运维

### Q38 怎么定位"这次任务为什么慢"？
Trace 树 + **按耗时排序**。我把 span 按 latency 降序排列，
瓶颈一眼可见。然后看它下面的子 span，是模型慢还是工具慢——
**这两个的优化手段完全不同**（模型慢 → 换小模型/缩短 prompt；
工具慢 → 加缓存/并发/换数据源）。

### Q39 你在监控哪些指标？
| 指标 | 回答什么问题 |
|---|---|
| P50/P95/P99 延迟 | 用户体验（平均值会骗人，尾部延迟才是真实体感） |
| 工具失败率 | Agent 稳定性（工具挂了 Agent 就是瞎子） |
| 缓存命中率 | 降本效果（缓存是性价比最高的优化） |
| 单任务 token / 成本 | 老板最关心的 ROI |
| 小模型路由占比 | 成本优化策略是否生效 |

### Q40 为什么 P95 比平均值重要？
平均值会被极端值掩盖。10 个请求里 9 个 100ms、1 个 10s，
平均 1.09s 看起来还行，但实际上每 10 个用户就有 1 个等了 10 秒。
**P95 = 95% 的请求都快于这个值**，更贴近用户真实体感。

## 十、如果面试官问"你觉得哪里做得不好"

**永远准备好这个问题**，这是送分题。诚实 + 有改进方案：

1. **工具是模拟的**：我用确定性模拟保证可复现和零外部依赖，
   生产要换成真实 API，并且要处理反爬、限流、增量抓取。
   但架构上只需替换 handler，Agent 侧零改动——这是我一开始就设计好的解耦。
2. **Checkpointer 用的是内存态**：演示够用，生产要换 PostgreSQL。
   代码里已经写好降级逻辑，改一行配置即可。
3. **没有做多租户隔离**：真实 SaaS 场景下，向量库要按租户分命名空间，
   否则会跨租户泄漏数据。
4. **Critic 有自我偏好偏差**：目前用大模型审小模型的产出（算是缓解），
   但严格来说应该用不同厂商的模型做交叉评审，或者加强人工抽样。
5. **成本数据是估算的**：用的是配置的价格表，
   生产应该以 API 返回的 usage 为准并做对账。
