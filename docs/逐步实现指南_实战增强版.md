## 开发顺序总览

代码顺序不是随手排的，它遵循一条铁律：

> **先定契约，再定能力，最后连流程。**

```
❌ 错误顺序：先写 Agent 的 prompt → 发现数据结构老变 → 全部推倒重写
✅ 正确顺序：契约 → 观测 → 模型能力 → 工具 → 记忆 → Agent → 编排 → 接口 → 评测
```

| 步骤 | 模块 | 文件 | 为什么在这个位置 |
|---|---|---|---|
| **S1** | 配置 + 数据契约 + 观测 | `app/core/` | 没有契约，后面所有代码都在猜数据结构；没有观测，出问题只能 print |
| **S2** | LLM 客户端 | `app/llm/client.py` | Agent 是它的消费者，必须先有稳定可靠的下层能力 |
| **S3** | 工具层 | `app/tools/registry.py` | 工具是 Agent 的"手"，要先有手 |
| **S4** | 记忆层 | `app/memory/` | Agent 的"脑子"，需要模型和工具被调用才能验证 |
| **S5** | Agent 角色 | `app/agents/roles.py` | 有模型、有工具、有记忆，才能写 Agent |
| **S6** | LangGraph 编排 | `app/graph/workflow.py` | Agent 是零件，编排是装配，装配必须在零件之后 |
| **S7** | API 层 | `app/api/routes.py` | 出口放在最后 —— 前面没跑通时接口一定是错的 |
| **S8** | 评测体系 | `app/eval/harness.py` | **最后写，但最重要** —— 没有基线无法证明任何优化有效 |
| **S9** | 部署与 CI | `Dockerfile` / `ci.yml` | 收口 |

## S1 · 契约层（配置 + 数据模型 + 观测）

### 做什么

三个文件，共 **571 行**：

- `app/core/config.py`（130 行）—— pydantic-settings 统一配置
- `app/core/schemas.py`（203 行）—— 全部跨模块数据结构
- `app/core/observability.py`（283 行）—— 链路追踪 + 指标采集

### 为什么先做这个

**设计要点：为什么先定 Schema 再写代码？**

LLM 的输出是**不确定的**。用 Pydantic 把"自由文本"约束成"结构体"，
是 LLM 工程化最核心的一招。结构体一旦定死：

- Agent 之间能用**类型安全**的方式传数据
- JSON 解析失败率从 ~15% 降到接近 0
- 这些模型同时是 API 响应契约，前后端不扯皮

**关键设计 1：`use_mock` 自动降级**

```python
@property
def use_mock(self) -> bool:
    if self.llm_provider == "mock":
        return True                      # ① 显式开关，CI 强制走 mock
    return not self.llm_api_key.startswith("sk-")   # ② 没 Key 自动降级
```

> **设计要点**：为什么要有自动降级？三个真实理由：
> ① CI 里绝不能真的花钱调模型 ② 单测需要确定性输出
> ③ 演示/答辩现场断网或余额不足时不能翻车。
> **生产项目里 mock provider 是标配，不是可选项。**

**关键设计 2：`Plan.topological_order()` 手写拓扑排序**

LangGraph 负责**节点级**编排，子任务 DAG 是**任务级**编排 —— 两层不同粒度。
用 Kahn 算法 O(V+E)，同时能检测环：

```python
def topological_order(self) -> list[SubTask]:
    by_id = {t.id: t for t in self.subtasks}
    indeg = {t.id: 0 for t in self.subtasks}
    for t in self.subtasks:
        for dep in t.depends_on:
            if dep in indeg:
                indeg[t.id] += 1
    queue = [tid for tid, d in indeg.items() if d == 0]
    order = []
    while queue:
        tid = queue.pop(0)
        order.append(by_id[tid])
        for t in self.subtasks:
            if tid in t.depends_on:
                indeg[t.id] -= 1
                if indeg[t.id] == 0:
                    queue.append(t.id)
    if len(order) != len(self.subtasks):
        raise ValueError("子任务依赖存在环，无法拓扑排序")
    return order
```

### ⚠️ 第一个大坑：TraceRecorder 放进 state 导致序列化崩溃

最初我把 `TraceRecorder` 放进了 `GraphState`，直接报错：

```
TypeError: Type is not msgpack serializable: TraceRecorder
```

**根因**：LangGraph 的 Checkpointer 会在**每个 super-step 后序列化整个 state**
（为了断点续跑），而 `TraceRecorder` 持有锁和对象，无法序列化。

**这是职责混淆的典型**：

| 数据类别 | 例子 | 该进 state 吗 |
|---|---|---|
| 业务数据 | 任务、计划、结果、评分 | ✅ 必须，且必须可序列化 |
| 运行时观测数据 | 追踪器、日志句柄、连接池、锁 | ❌ 绝不 |

**修复**：新建 `app/core/context.py`，用 `contextvars` 承载追踪器：

```python
_tracer_var = contextvars.ContextVar("tracer", default=None)

def set_tracer(tracer) -> contextvars.Token:
    return _tracer_var.set(tracer)

def reset_tracer(token) -> None:
    _tracer_var.reset(token)   # 必须 reset，否则污染事件循环
```

> **设计要点**：为什么不用全局变量？全局变量在 asyncio 并发下会互相覆盖 ——
> A 请求的 span 会被 B 请求写进去。`threading.local` 也解决不了，
> 因为 asyncio 是单线程多协程，同线程内多个协程共享它。
> `contextvars` 正是 PEP 567 为此设计的：**协程级隔离，语义等同"异步版 thread-local"**。

## S2 · LLM 客户端层（530 行）

### 做什么

`app/llm/client.py` —— 全项目最底层的能力层：

1. **统一抽象** `LLMClient` —— 业务不关心背后是 qwen / GPT / vLLM
2. **模型路由** `ComplexityRouter` —— 4 因子加权打分
3. **指数退避重试** —— tenacity + jitter
4. **结构化输出** `chat_structured()` —— 解析-校验-修复循环
5. **流式生成** `chat_stream()` —— 长文写作专用（**今日实测新增**）

### 关键设计 1：连接池复用

```python
async def _get_client(self, base_url: str, api_key: str) -> AsyncOpenAI:
    key = f"{base_url}|{api_key[:8]}"
    async with self._lock:
        if key not in self._clients:
            self._clients[key] = AsyncOpenAI(
                base_url=base_url, api_key=api_key,
                timeout=settings.llm_timeout,
                max_retries=0,   # 重试我们自己做，避免双重重试放大流量
            )
        return self._clients[key]
```

> **设计要点**：为什么缓存 client？`AsyncOpenAI` 内部维护 httpx 连接池，
> 每次 new 一个会丢连接复用，高并发下 TIME_WAIT 暴涨。

### 关键设计 2：结构化输出的"解析-校验-修复"循环

```python
for attempt in range(max_fix_attempts + 1):
    raw, used_model = await self.chat(msgs, ...)
    try:
        data = extract_json(raw)
        return schema.model_validate(data), used_model
    except (LLMFormatError, ValidationError, json.JSONDecodeError) as exc:
        # 把错误信息拼回 prompt，让模型自我修正
        ...
```

`extract_json()` 要处理模型的各种"格式幻觉"：markdown 代码块包裹、前缀废话、
尾逗号、中文字段名。**这套机制不是锦上添花，是必需品** —— 模型有 5%~15% 概率输出非法 JSON。

### 🔥 关键设计 3：`chat_stream()` —— 今日实测新增（最有价值）

**现象**：用真实模型 qwen3.8-flash 跑，长文生成反复超时：

```
16:04:51 | Retrying LLMClient.chat._call in 1.84 seconds as it raised LLMTimeoutError
16:08:10 | Retrying LLMClient.chat._call in 1.62 seconds as it raised LLMTimeoutError
```

**实测数据（关键证据，可复现）**：

| 探针 | 输出规模 | 耗时 |
|---|---|---|
| 短输出（流式） | 59 字 | **1.8 s** |
| **长输出（流式）** | **9,701 字** | **227.1 s** |

> 由 `scripts/bench_latency.py` 生成，归档于 `docs/bench_latency_result.md`，可复跑。

**长短延迟差了 126 倍！**

**根因**：`httpx` 的 `timeout` 在**非流式**请求下约束的是"首字节→完整响应"的**总时长**。
模型正常在生成（近万字需 200s+），但客户端 60s 就掐断了。

**更严重的隐藏代价**：掐断后触发重试，**同一个超长请求被重新发起 3 次**，
token 被重复计费 —— **这个 bug 不只是"慢"，它让成本翻了三倍**。

**修复（两步，第二步才是关键）**

第一步：超时从 60s → 180s（治标）：

```python
# 为什么默认给到 180s 而不是 60s？
# 新一代推理型模型（qwen3.8 系列默认开启深度思考）生成长文本时，
# 单次调用 60~130s 是常态。压到 60s 会产生大量「非故障性超时」。
# 后果比慢更糟：掐断后触发重试，同一请求被重复计费三次，成本翻三倍。
llm_timeout: int = 180
```

第二步（**真正的解法**）：新增流式方法，Writer 改用它：

```python
async def chat_stream(self, messages, *, span=None, tracer=None, ...):
    """
    设计要点：为什么长文写作必须用流式，而不是把 timeout 调大？
    非流式下 httpx 的 timeout 是「首字节到完整响应」的总时长约束。
    流式的本质区别：服务端一有 token 就立刻推回来。
    此时 read timeout 约束的是「两个 chunk 之间的最大间隔」，
    而不是「整个响应的总时长」。
    只要模型持续吐字（间隔远小于 timeout），生成 10 分钟也不会被判超时。
    这就是「用正确的机制，而不是调大参数」——调参治标，换机制治本。
    """
    stream = await client.chat.completions.create(
        model=model, messages=messages, stream=True,
        stream_options={"include_usage": True},   # 流式下拿 usage 必须显式开
    )
    async for chunk in stream:
        usage = getattr(chunk, "usage", None)
        if usage:
            pt = usage.prompt_tokens or pt
            ct = usage.completion_tokens or ct
        if chunk.choices and chunk.choices[0].delta.content:
            chunks.append(chunk.choices[0].delta.content)
```

**验证效果**：修复后近万字长文 **227.1 秒成功返回**（修复前必超时）。

> **一句话回答**：遇到超时，初级反应是"把 timeout 调大"，但那是在跟模型速度赛跑，
> 且超时后重试会让成本翻倍。正确做法是**换机制** —— 流式把约束从"总时长"
> 改成"chunk 间隔"。**调参治标，换机制治本。**

### 关键设计 4：模型路由

```python
class ComplexityRouter:
    @staticmethod
    def pick(role: str, text: str) -> tuple[str, bool]:
        score = role_weight * 0.4 + length_factor * 0.3 + keyword_bonus * 0.3
        use_small = score < settings.model_routing_threshold
        return (settings.llm_small_model if use_small else settings.llm_model), use_small
```

> **设计要点**：路由降本的量化。
> qwen3.8-flash（0.8元/M 输入）vs qwen3.8-max（12元/M 输入）差 **15 倍**。
> 项目中约 70% 调用是简单任务（工具参数、抽取、分类），路由后整体成本约降到全用大模型的 **1/8**。

### 为什么 Agent 需要工具而不是让模型硬答

> **设计要点**：模型的知识是静态的、会幻觉的。
> 凡是「可计算、可查询、需实时」的事，都必须走工具（Tool Calling）。
> 模型只负责**决策用哪个工具、传什么参数**。
> Anthropic 提出的 MCP（Model Context Protocol）就是把这套标准化：
> 统一 schema + 统一发现机制 + 统一调用协议。

### ⚠️ 三个真实坑（全部已修复）

**坑 A（最严重）· 安全拦截后仍返回 `ok=True`**

```python
result = await registry.call("sql_query", {"sql": "DROP TABLE orders"})
assert result.ok is True     # ← 通过了？！安全拦截形同虚设
```

**根因**：`ToolCall.ok` **默认值是 `True`**，而 `break` 跳出循环时没有显式置为 False：

```python
except (PermissionError, ValueError) as exc:
    last_err = f"{type(exc).__name__}: {exc}"
    metrics.tool_errors += 1
    break                # ← 只 break，ok 还是 True！
```

**这是"依赖默认值"的经典陷阱** —— 默认值 `True` 在正常路径下是对的，
但在异常路径下变成了一个**沉默的错误承诺**。

**修复**：不依赖任何默认值，改用"是否真的拿到结果"作为唯一判据：

```python
if record.result is None and record.error is None:
    record.ok = False
    record.error = last_err or "工具执行失败且未返回错误信息"
elif last_err is not None and record.result is None:
    record.ok = False
    record.error = last_err
```

> **实践意义**：**静默失败比崩溃更危险** —— 崩溃能被监控发现，
> 静默失败会被当成成功数据流向下游。电商场景里，一次静默失败可能造成真实资损。

**坑 B · 安全异常被当成可重试异常，白等 1.3 秒**

`PermissionError`（安全拒绝）和 `ValueError`（参数非法）是**确定性失败**：
输入不变，结果永远不会变。重试只是浪费时间和配额。

```python
except (PermissionError, ValueError) as exc:
    last_err = ...       # 确定性失败：不重试
    break
except TypeError as exc:
    last_err = ...       # 代码缺陷：不重试
    break
except asyncio.TimeoutError:
    last_err = ...       # 瞬时失败：重试
    await asyncio.sleep(backoff)
    continue
```

> **设计要点**：重试的前提是"失败是瞬时的、且重试可能改变结果"。

**坑 C · 参数校验依赖 `TypeError` 导致非法参数被静默忽略**

`competitor_scraper` 所有参数都可选，传 `wrong_arg=1` 时 Python 不报错，
非法参数被**静默丢弃**，Agent 拿到全量数据，结论失效但链路不报错。

**修复**：调用前用 JSON Schema 预校验必填项 + 字段白名单：

```python
missing = [k for k in spec.parameters.get("required", []) if k not in arguments]
if missing: return _fail(record, f"缺少必填参数: {missing}")

allowed_props = set(spec.parameters.get("properties", {}).keys())
unknown = [k for k in arguments if k not in allowed_props]
if unknown: return _fail(record, f"未知参数: {unknown}，允许的参数为: {sorted(allowed_props)}")
```

### 🔥 今日实测补充：把约束写进工具描述

真实模型第一次跑时出现：

```
16:03:37 | WARNING | 工具参数非法: competitor_scraper -> ['marketplace', 'include_keywords']
16:03:37 | WARNING | 工具参数缺失: review_insight -> ['product_id']
```

模型自作主张传了 schema 里没有的参数，还漏了必填项。

**注意**：这恰恰证明**坑 C 的防御机制是对的** —— 它把错误明确报了出来。

**修复**：把隐含前提显式写进 description：

```python
description=(
    "抓取指定品类在亚马逊美国站的竞品榜单...调用时只需传入 category（品类关键词），"

```

**修复后**：执行 10+ 次调用，**未再出现参数非法告警**。

> **一句话回答**：Function Calling 的可靠性 = schema 正确 **+ 描述无歧义**。
> 模型犯错往往不是能力问题，而是**信息不足**。

## S4 · 记忆层（283 + 101 行）

### 三层记忆

| 层 | 机制 | 解决什么 |
|---|---|---|
| **L1 短期** | 滑动窗口（最近 N 条） | 多轮对话指代消解 |
| **L2 摘要** | 超阈值触发压缩 | Token 成本 O(n²) 问题 |
| **L3 长期** | 向量检索（哈希词袋，dim=256） | 跨任务复用结论 |

> **设计要点**：为什么不能只靠"把全部历史塞进 prompt"？
> Token 成本是 O(n²) 增长的 —— 第 20 轮的 prompt 里有前 19 轮的全部内容。
> L2 摘要压缩把线性增长的上下文压成常数级，这是成本控制的关键。

`build_task_context()` 做**依赖驱动的最小上下文注入** —— 只把当前子任务依赖的前置结果注入。

## S5 · Agent 角色层（699 行）

| Agent | 职责 | 关键设计 |
|---|---|---|
| `PlannerAgent` | 拆解任务为 DAG | MAX_SUBTASKS=6，`_sanitize()` + `_fallback_plan()` 兜底 |
| `ResearcherAgent` | 3 跳调研 | `asyncio.gather` 并发 |
| `AnalystAgent` | 数据分析与洞察 | 事实约束，禁止编造 |
| `WriterAgent` | 内容创作 | **`chat_stream` 长文生成**，固定大模型 |
| `CriticAgent` | 质量评审 | 4 维度加权，阈值 0.80，**硬覆盖模型的 passed** |
| `ReviewerAgent` | 终审与合规 | 硬性合规拦截 |

### Multi-Agent 到底比单 Agent 强在哪

> **设计要点（本项目最核心的设计题）**：三个真实收益，一个真实代价。

**收益 1 · 角色分离降低认知负载**
写一段"既要分析数据又要写文案又要自我检查"的 prompt，模型会顾此失彼。
拆成三个 Agent，每个 prompt 只专注一件事 —— 对应**单一职责原则**。

**收益 2 · 上下文隔离防止错误累积**
多 Agent 各自独立上下文，避免错误在长上下文里被反复放大。

**收益 3 · 可独立评测**
可以单独测 Critic 的评审准确率，而不是只能测端到端。

**代价 · 成本和延迟增加**
多 Agent = 更多 LLM 调用。所以必须配套**模型路由**（简单角色走小模型）
和**反思轮次上限**（`MAX_REFLECTION_ROUNDS=2`，防止无限循环烧钱）。

### 关键设计：Critic 的硬覆盖

```python
# 不信任模型自评的 passed，用加权分数自己判定
score = factuality*0.3 + compliance*0.3 + relevance*0.2 + readability*0.2
critique.passed = (score >= self.pass_threshold) and not critique.fatal
```

> **设计要点**：多 Agent 怎么防止"错误互相放大"？
> Critic 独立打分 + **硬阈值回灌重跑**。且**不信模型自评的结论，只信加权计算的结果**。

### 关键设计：最小权限

每个 Agent 有 `allowed_tools` 白名单 —— Researcher 只能调用调研类工具。
**这是安全边界，不是可选项。**

## S6 · LangGraph 编排层（710 行）

### 图结构

```
prepare → planner → execute → [route_after_execute]
                                    ↓
                                 writer → critic → [route_after_critic]
                                                      ↓            ↓
                                                   revise        finalize
                                                      ↓
                                                 (回到 critic)
```

### 为什么用 LangGraph 而不是自己写 while 循环

> **设计要点**：自己写循环能跑，但会缺三样企业级必需的东西：
> ① **检查点**：每个 super-step 后自动持久化，进程挂了能续跑
> ② **可观测**：每个节点是独立 span，天然可追踪
> ③ **可视化**：图结构能导出 Mermaid，评审/交接成本低
>
> 且 StateGraph 是**显式状态机**，比隐式 while 循环更容易推理。

### 关键设计 1：Reducer 做并行状态合并

```python
class GraphState(TypedDict):
    results: Annotated[list, _merge_results]   # 并行节点写同一字段靠 reducer 合并
```

### 关键设计 2：并发执行同批次子任务

```python
# 设计要点：为什么用 asyncio.gather 并发而不是 for 串行？
# 6 个子任务串行 = 6 倍耗时。并发后总耗时 ≈ 最慢的那个。
# 注意生产要用 Semaphore 限流，避免打爆下游或撞 API 限速。
gathered = await asyncio.gather(*tasks, return_exceptions=True)
```

### 关键设计 3：循环反思 + 硬上限

```python
if critique and not critique.passed and rounds < settings.max_reflection_rounds:
    return "revise"     # 条件边 → 回到 writer 重写
return "finalize"
```

> **为什么必须有硬上限**？否则 Critic 一直不通过就会无限循环，
> **每分钟都在烧钱**。这是 Agent 系统必须有的"经济性刹车"。

`ZhinaoRunner.run()` 返回 trace；`resume()` 从 Checkpointer 恢复。

## S7 · API 层（327 行）

### 三种运行模式

```python
POST /run?mode=sync        # 同步（短任务、调试）
POST /run?mode=background  # 后台任务（返回 task_id，长任务）
POST /run?mode=sse         # SSE 流式（实时推送进度）
```

> **设计要点**：
> **Q: 为什么 Agent 服务必须用流式（SSE）？**
> Agent 任务动辄几十秒到几分钟（**今日实测：单任务 10 分钟+**）。
> 普通请求会：① 前端一直转圈 ② Nginx 默认 60s 超时直接 504 ③ 用户无法中断。
> 选 SSE 而非 WebSocket：单向推送够用、基于 HTTP 无需协议升级、能穿透大多数企业网关。
>
> **Q: 长任务为什么要后台队列而不是直接 await？**
> HTTP 连接扛不住分钟级等待。这也反向印证了今日实测：
> **一个跑十几分钟的 Agent 工作流，用同步 HTTP 一定会被网关掐断。**

### SSE 实现要点

```python
yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"
# 关键：设置 X-Accel-Buffering: no，否则 Nginx 会缓冲导致"流式失效"
# 定期发心跳防止连接被中间层判定为空闲断开
```

## S8 · 评测体系（531 行）—— 本项目最值钱的部分

> **设计要点（先说结论）**：90% 的应届生项目只能演示"能跑通"，
> 但答不上这五个问题：
> 1. 你怎么知道改完之后效果变好了？（没有基线，无法对比）
> 2. 变好多少？（没有指标，全靠感觉）
> 3. 是不是只在这一条 case 上变好了？（没有测试集，无法验证泛化）
> 4. 上线后怎么保证不退化？（没有回归门禁，改一个 prompt 就可能悄悄变差）
> 5. 评测本身可信吗？（没有校准，可能是个橡皮图章）

### 四层评测

| 层 | 机制 | 特点 |
|---|---|---|
| **L1 确定性断言** | 关键词命中、字段完整性、格式合法性 | 快、准、零成本 |
| **L2 Agent 行为指标** | 子任务数、工具调用次数、重试次数 | 看"过程"而非"结果" |
| **L3 LLM-as-Judge** | 另一个模型按 rubric 打分 | 覆盖语义质量 |
| **L4 人工校准** | 人工抽检对比 L3 打分 | 校准 Judge 是否可信 |

**分层原则**：**能用确定性规则判的绝不用模型判**，模型判的必须有抽检兜底。

### 关键洞察：mock 模式下通过率只有 40-60%，这不是 bug

> mock 模型返回固定占位文本，不含业务关键词 → L1 断言必然部分失败。
> **这恰恰是评测在正常工作的证据。**
> 如果任何输入都 100% 通过，说明评测指标失效了。
>
> **简历上的评测数据必须用真实模型跑出来**，不能用 mock 数据充数。

## 今日实战总结：真实模型跑通后的 5 条收获

1. **超时参数必须按"最慢负载"设计，而不是平均负载** —— 长短差两个数量级，平均值会骗人。
2. **长文生成一律走流式** —— 这是机制选择，不是参数调整。
3. **超时的真实代价是成本，不只是延迟** —— 重试会重复计费，这个账很容易被忽略。
4. **Function Calling 的可靠性 = schema 正确 + 描述无歧义** —— 后者常被低估。
5. **同步 HTTP 扛不住分钟级 Agent 工作流** —— 异步 + SSE 是必选项而非加分项。
