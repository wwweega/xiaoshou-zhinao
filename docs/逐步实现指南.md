# 运营智脑 · 逐步实现指南

> 这份文档回答一个具体问题：**如果我从零开始，为什么按这个顺序写代码？**
> 每一节都包含「这一步做什么 → 为什么现在的顺序最好 → 容易踩的坑」。

---

## 为什么是这个顺序？

代码顺序不是随手排的，它遵循一条原则：**先定契约，再定能力，最后连流程。**

```
错误的顺序：先写 Agent 的 prompt → 发现数据结构老变 → 全部重写
正确的顺序：契约 → 观测 → 模型能力 → 工具 → 记忆 → Agent → 编排 → 接口 → 评测
```

| 步骤 | 模块 | 为什么在这个位置 |
|---|---|---|
| 1 | 配置 + 数据契约 + 观测 | 没有契约，后面所有代码都在猜数据结构；没有观测，出了问题只能 print |
| 2 | LLM 客户端 | Agent 是它的消费者，必须先有稳定可靠的下层能力 |
| 3 | 工具层 | 同上，工具是 Agent 的"手"，要先有手 |
| 4 | 记忆层 | Agent 的"脑子"，需要模型和工具被调用才能验证 |
| 5 | Agent 角色 | 有模型、有工具、有记忆，才能写 Agent |
| 6 | LangGraph 编排 | Agent 是零件，编排是装配，装配必须在零件之后 |
| 7 | API 层 | 出口放在最后，前面没跑通时接口一定是错的 |
| 8 | 评测体系 | **最后写但最重要**——没有基线就无法证明任何优化有效 |
| 9 | 部署与 CI | 收口 |

**注意第 8 步的位置**：虽然是最后写的，但它是整个项目价值的放大器。
如果没有它，前 7 步做的所有优化（路由、缓存、上下文压缩）你都**无法证明有效**。

## Step 1 · 配置层 + 数据契约 + 观测层

**做了什么**
- `app/core/config.py`：pydantic-settings 统一管理配置，`use_mock` 自动降级
- `app/core/schemas.py`：所有跨模块传递的数据结构 + DAG 拓扑排序
- `app/core/observability.py`：TraceRecorder（调用树） + MetricsCollector（P50/P95）

**为什么这么排**
契约先行是软件工程的基本功。LLM 项目的特殊性在于：
模型的输出是不确定的，所以**契约比传统项目更重要**——
你必须把"自由文本"强制约束成"结构体"，否则下游全是 try/except。

**常见疑问**
- 为什么用 `lru_cache` 做配置单例，不用模块级变量？
  → 模块级变量在 import 时执行，测试里不好替换；lru_cache 可显式 clear() 注入测试配置
- P95 怎么算？
  → 排序取第 ⌈0.95n⌉ 位。关注尾部延迟，因为平均值会被极端值掩盖
- Trace 里的 parent_span_id 有什么用？
  → 构建调用树，能回答"慢在哪一跳"。这就是分布式追踪的基本模型

## Step 2 · LLM 客户端（模型路由 + 重试 + 结构化输出）

**做了什么**
- `ComplexityRouter`：四因子加权打分，<0.5 走小模型
- 指数退避 + 抖动重试（429/超时）
- `chat_structured`：结构化输出 + 失败回灌修复
- `extract_json`：处理模型的各种"脏输出"

**为什么在这里**
Agent 层要调用 LLM，所以必须先把 LLM 调用的三大难题解决掉：
①模型不稳定（重试）②输出格式乱（解析修复）③太贵（路由）。
如果这层不可靠，上层写得再漂亮也没用。

**常见疑问**
- 为什么用抖动（jitter）？
  → 固定间隔重试会让所有失败请求同时重试（惊群效应），把下游打得更惨
- 为什么 `max_retries=0` 传给 AsyncOpenAI？
  → 避免双重重试（SDK 一层 + 我们一层），放大流量
- `extract_json` 处理了哪几种情况？
  → 代码块包裹 / 前面有寒暄 / 尾逗号 / 嵌套引号
- 这个函数有什么价值？
  → 真实项目里 90% 的"模型不稳定"其实是格式问题，不是智能问题

## Step 3 · 工具层

**做了什么**
- `ToolSpec`：统一工具描述，转成 Function Calling schema
- `ToolRegistry.call`：统一入口，做校验/超时/重试/幂等/权限/指标
- 12 个工具，全部确定性模拟

**为什么在这里**
工具有两类消费者：Agent（要调）和评测（要验）。
先建好工具，Agent 层才能"有东西可用"。

**常见疑问**
- 为什么所有调用必须走同一个入口？
  → 只有收口才能统一做 trace/超时/重试/缓存/校验/指标
- 参数错误为什么不重试？
  → 重试还是错的，浪费时间；应该回灌 schema 让模型重新决策
- 幂等缓存怎么做并发安全？
  → per-key 的 asyncio.Lock，防缓存击穿
- 模型生成的 SQL 直接执行安全吗？
  → 绝不安全。只读校验+白名单+行数上限+超时，生产还要独立只读账号

---

## Step 4 · 记忆层

**做了什么**
- `ConversationMemory`：L1 窗口 + L2 结构化摘要压缩
- `LongTermMemory`：L3 哈希词袋向量 + 余弦相似度召回 + 结构化事实双写
- `build_task_context`：依赖驱动的最小上下文
- `build_checkpointer`：自动降级（PG → 内存）

**为什么在这里**
记忆需要调用 LLM（做摘要），所以要在客户端之后。

**常见疑问**
- 为什么不能让 Agent 记住全部历史？
  → O(n²) token 成本 + 注意力稀释（lost in the middle）
- 摘要为什么必须结构化？
  → 自由总结会丢关键实体（品牌名、数字）；结构化可逐项检查是否丢失
- 相似度阈值为什么必须有？
  → 不设阈值永远能召回 Top-K，垃圾也会进上下文
- 为什么长期记忆要双写向量+事实表？
  → 向量擅长模糊语义，事实表擅长精确查询；这和混合检索同源

## Step 5 · Agent 角色

**做了什么**
- `BaseAgent`：收口横切关注点（trace / 异常兜底 / 工具权限）
- 6 个 Agent：Planner / Researcher / Analyst / Writer / Critic / Reviewer

**为什么在这里**
模型、工具、记忆都就位了，才能写 Agent。
如果先写 Agent，你会反复改 prompt 来适配"还没有的接口"。

**常见疑问**
- Multi-Agent 比单 Agent 强在哪？
- 代价是什么？（延迟、成本、误差累积、调试难）
- Critic 的 prompt 为什么要和 Writer 不同？
  → 同视角盲区相同，发现不了自己的系统性问题
- 为什么 Critic 不给它工具权限？
  → 最小权限原则；评审者不该引入新信息，否则它可能"自己创造证据来通过"

---

## Step 6 · LangGraph 编排（心脏）

**做了什么**
- `GraphState` + 两个自定义 reducer
- 7 个节点 + 2 条条件边（批次推进循环 + 反思回灌循环）
- `next_ready_subtasks`：任务级 DAG 批次调度
- 越改越差的自动回滚

**为什么在这里**
Agent 是零件，编排是装配。零件没做好，装配出来的东西一定有问题。

**常见疑问**
- 为什么用 LangGraph？
- 什么是 super-step？
  → 所有当前可执行节点并发跑一轮 + 状态合并，Pregel 风格 BSP 模型
- 不用 reducer 会怎样？
  → 并行 super-step 里后写覆盖，偶发丢数据。单测过、并发炸，最难查的 bug
- 断点续跑怎么做到？容易答错什么？
  → 不只是有 thread_id；还要状态可序列化 + 图结构不变（要版本化图）
- 节点级并行 vs 任务级并行？
  → 两层不同粒度，这是很多人混淆的点

---

## Step 7 · API 层

**做了什么**
- 三种调用模式：同步 / 后台任务 / SSE 流式
- 观测接口：`/api/metrics`、`/api/traces`、`/api/trace/{id}`
- 工具调试接口、记忆检索接口

**为什么在这里**
前面都跑通了，接口才有意义。否则你会在调试接口 bug 和逻辑 bug 之间反复横跳。

**常见疑问**
- 为什么用 SSE 不用 WebSocket？
- SSE 的五个坑？（Nginx 缓冲 / 代理超时 / 断连检测 / 心跳 / 格式）
- lifespan 里该做什么不该做什么？
  → 该：连接池、配置校验。不该：耗时预热（K8s 探针会判定启动失败）
- 客户端断了怎么办？
  → 捕获 CancelledError 并取消任务，否则继续烧 token

## Step 8 · 评测体系

**做了什么**
- L1 确定性断言 / L2 Agent 行为指标 / L3 LLM 裁判 / L4 人工校准
- 20 条用例（含 3 条 critical 合规红线）
- `Evaluator.render` 生成 Markdown 报告
- CI 门禁规则

**为什么放在最后但最重要**
**因为它是放大前 7 步价值的杠杆。**
没有评测：你说"我优化了检索"→ "好多少"→ 答不上来
有评测：你说"Recall 从 0.61 到 0.89，500 条金标集，口径如下"→ 可信度天差地别

**常见疑问**
- 三层评测为什么以 L1/L2 为主？
  → 便宜、稳定、可进 CI；LLM 打分贵且有偏差，只适合抽样
- LLM-as-Judge 的三个偏差？怎么缓解？
- 怎么证明 judge 可信？
  → 人工抽样算 MAE，<0.1 才可用。**说不出这个说明你只是"用了"，不是"建了体系"**
- 什么是静默退化？为什么必须进 CI？
  → 改一句 prompt，90% case 正常但某类场景崩了，只有回归门禁能拦

---

## Step 9 · 部署与 CI

**做了什么**
- Dockerfile（非 root、健康检查、层缓存优化）
- docker-compose（app + postgres + redis + 资源限制）
- GitHub Actions（测试 + 评测门禁 + 镜像构建）

**常见疑问**
- 为什么依赖要先 COPY requirements 再 COPY 代码？
  → Docker 层缓存：改代码不用重装依赖，构建从 3min 降到 10s
- 为什么要设资源限制？
  → 一个内存泄漏的 Agent 能拖垮整机（noisy neighbor）
- CI 里怎么避免真的花钱调 API？
  → `LLM_PROVIDER=mock`，这也是我写 mock provider 的三大理由之一

## 现在请你做的事（按顺序）

```bash
cd xiaoshou-zhinao

# ① 装依赖
pip install -r requirements.txt

# ② 跑单测（验证核心逻辑，不花钱）
python -m pytest tests/ -v

# ③ 配 .env 后跑一次真实任务
cp .env.example .env    # 然后填 Key
python -m scripts.demo

# ④ 跑评测，拿到你的第一份真实数据
python -m scripts.run_eval --limit 6 --no-judge

# ⑤ 启动服务，打开前端看 Trace
python -m uvicorn app.main:app --port 8000

# ⑥ 把 ③④⑤ 的真实数字填进 README 的「实测数据」表
```

**第 ⑥ 步最重要**：填完那张表，这个项目才能写进简历。
没填之前，它只是代码；填完之后，它是**可验证的工程成果**。
