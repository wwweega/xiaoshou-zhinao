| 探针 | 输出规模 | 耗时 | 结论 |
|---|---|---|---|
| **A · 短输出（流式）** | 59 字 | **1.8 s** | 基础延迟很低 |
| **B · 长输出（流式）** | **9,701 字** | **227.1 s** | 长文生成必须流式 |

### 这组数据推翻了一个想当然的假设

**假设**：LLM 调用"几秒钟就返回"，timeout 设 60s 绰绰有余。

**实际**：qwen3.8-flash 默认开启深度思考，生成近万字长文需要 **227 秒（约 3.8 分钟）**。
短输出 1.8s 和长输出 227.1s 之间差了 **126.5 倍** ——
用同一个 timeout 值覆盖两种负载，必然有一边是错的。

**这是"平均值陷阱"的典型案例**：只看短请求延迟去定超时参数，
长请求就会周期性失败，且失败原因表现为"网络超时"，极易误判成网络问题。

## 四、全链路耗时构成（36 个 span 实测拆解）

从 trace 文件 `data/traces/tr_85e50d9c1118.json` 提取的真实数据：

### 按 span 类型汇总

| 类型 | 数量 | 合计耗时 | 均值 |
|---|---|---|---|
| `agent` | 13 | 2134.6 s | 164.2 s |
| `node` | 13 | 1396.7 s | 107.4 s |
| `tool` | 10 | 0.0 s | 0.0 s |

> **重要发现**：**工具执行耗时几乎为零（0.0s）**，因为本项目工具是本地模拟实现。
> 真实场景里如果接外部 API，工具耗时会显著上升 —— 这恰恰说明**瓶颈全在 LLM 调用**。

### 顶层节点耗时（这才是关键）

| 节点 | 耗时 | 说明 |
|---|---|---|
| `prepare` | 0.0 s | 上下文准备 |
| `planner` | 22.0 s | 任务拆解 |
| `execute` (第1批) | 40.1 s | 子任务 t1 |
| `execute` (第2批) | 85.5 s | 子任务 t2/t3 |
| `execute` (第3批) | 64.0 s | 子任务 t4 |
| `execute` (第4批) | 256.6 s | 子任务 t5（Writer 长文生成）|
| `critic` (第1轮) | 97.9 s | 评审 |
| **`revise` (第1轮)** | **377.1 s** | **重写（最长）** |
| `critic` (第2轮) | 64.2 s | 复评 |
| **`revise` (第2轮)** | **321.2 s** | **再次重写** |
| `critic` (第3轮) | 68.1 s | 通过 |
| **总计** | **1396.7 s ≈ 23 分钟** | |

### 三个关键洞察

**洞察 1 · 反思循环是最大的时间黑洞**

两轮 `revise` 合计 **698 秒**，占总耗时的**一半**。
这说明：**Critic 阈值（0.80）设得偏严**，导致反复重写。

> **面试话术**：这就是为什么 Agent 系统必须设反思轮次上限
> （项目里是 `MAX_REFLECTION_ROUNDS=2`）。
> 没有上限的话，Critic 一直不通过就会无限重写，**每分钟都在烧钱**。
> 而且这里有个权衡：阈值高 → 质量好但慢且贵；阈值低 → 快且省但质量差。
> 理性的做法是**用评测数据找拐点**，而不是拍脑袋定 0.8。

**洞察 2 · 长文生成（Writer）是单点最慢环节**

`execute` 第 4 批 256.6s、两轮 `revise` 各 377s / 321s ——
**全是 Writer 在生成长文**。这直接印证了流式改造的必要性。

**洞察 3 · 规划阶段很快（22s）**

Planner 输出的是小 JSON，不需要长生成，所以快。
**这验证了模型路由的合理性**：简单结构化任务确实便宜又快，没必要用大模型。

## 五、踩坑与修复（3 个真实问题）

### 坑 1 · `llm_timeout=60` 导致长文生成反复超时

**现象**

```
16:04:51 | Retrying LLMClient.chat._call in 1.84 seconds as it raised LLMTimeoutError
16:08:10 | Retrying LLMClient.chat._call in 1.62 seconds as it raised LLMTimeoutError
16:10:12 | Retrying LLMClient.chat._call in 2.55 seconds as it raised LLMTimeoutError
```

**根因**：`httpx` 的 `timeout` 在**非流式**请求下约束的是"首字节 → 完整响应"的**总时长**。
模型正常在生成（近万字长文需 200s+），但客户端 60s 就掐断了。

**更严重的隐藏代价**：掐断后触发重试，**同一个超长请求被重新发起 3 次**，
token 被重复计费 —— **这个 bug 不只是"慢"，它让成本翻了三倍**。

**修复（两步，第二步才是关键）**

第一步：超时从 60s → 180s（治标）：

```python
# 为什么默认给到 180s 而不是 60s？
# 新一代推理型模型（qwen3.8 系列默认开启深度思考）生成长文本时，
# 单次调用 60~130s 是常态。压到 60s 会产生大量「非故障性超时」。
# 后果比慢更糟：掐断后触发重试，同一请求被重复计费三次，成本翻三倍。
llm_timeout: int = 180
```

第二步（**真正的解法**）：新增 `chat_stream()`，Writer 改用它。

```python
# 流式的本质区别：服务端一有 token 就立刻推回来。
# 此时 read timeout 约束的是「两个 chunk 之间的最大间隔」，
# 而不是「整个响应的总时长」。
# 只要模型持续吐字（间隔远小于 timeout），生成 10 分钟也不会被判超时。
```

**修复效果验证**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 长文生成（近万字）| **超时失败** | **227.1s 成功返回**（见 `bench_latency_result.md`）|
| 全链路超时重试次数 | 每轮 2~3 次 | **0 次** |

> **面试话术**：遇到超时，初级反应是"把 timeout 调大"，但这是在跟模型速度赛跑，
> 而且超时后的重试会让成本翻倍。正确做法是**换机制** —— 流式把约束从"总时长"
> 改成"chunk 间隔"，这才是长文生成的正确姿势。**调参治标，换机制治本。**

### 坑 2 · 模型给工具传了不存在的参数名

**现象**

```
16:03:37 | WARNING | 工具参数非法: competitor_scraper -> ['marketplace', 'include_keywords']
16:03:37 | WARNING | 工具参数缺失: review_insight -> ['product_id']
```

模型自作主张给 `competitor_scraper` 传了 schema 里**没有**的参数；
调 `review_insight` 时**漏掉了必填的** `product_id`。

**根因（两层）**

1. **Schema 描述不够显式**：没写清"站点固定为美国站"，模型就猜可能支持其他站点。
2. **`product_id` 语义模糊**：模型不知道去哪拿 ASIN，干脆不传。

**关键认识**：这一层的**防御机制是正确的** ——
正是之前修的「坑 4」（`registry.py` 的 Schema 预校验），
把这个错误**明确报了出来**，而不是静默用默认值跑出一份错数据。

**修复：用自然语言补 schema 的表达力**

```python
description=(
    "抓取指定品类在亚马逊美国站的竞品榜单...调用时只需传入 category（品类关键词），"
    "不要自行添加 marketplace、include_keywords 等参数——站点固定为亚马逊美国站。"
)
```

```python
"product_id": {
    "type": "string",
    "description": "商品 ID 或 ASIN；缺失时可用商品名/品类关键词代替",
},
```

**效果**：修复后完整跑完全流程，**告警数 = 0**（修复前 2 处）。

> **面试话术**：Function Calling 的可靠性不只是"schema 写得对"，
> 更要"**schema 写得让模型不会猜错**"。
> 模型犯错往往不是能力问题，而是**信息不足** —— 它不知道站点是固定的，
> 也不知道 ASIN 可以降级代替。把隐含前提显式写进 description，
> 比事后做参数校验更早地解决问题。

### 坑 3 · 全链路耗时 23 分钟（不是 bug，是负载特性）

**现象**：单条任务端到端 **1397 秒（≈23 分钟）**。

**根因**：这是**真实负载特性**，不是代码问题。拆解如下：

```
Planner  规划      :   22.0 s
Execute  子任务×5  :  446.2 s   （其中 Writer 长文 256.6s）
Critic   评审×3    :  230.2 s
Revise   重写×2    :  698.3 s   ← 最大头
----------------------------------------
合计               : 1396.7 s ≈ 23 分钟
```

**处理方式（这是工程判断，不是"debug"）**

1. **调整预期**：真实 LLM 项目不是"秒回"，尤其带多轮反思的 Agent 工作流。
2. **反证异步架构的必要性**：这证明了项目里 `/run?mode=background` 和 SSE 流式接口
   的设计是对的 —— **同步等待 23 分钟的 HTTP 请求在生产环境必然被网关掐断**
   （Nginx 默认 60s 超时）。
3. **反思阈值需要数据驱动调优**：两轮重写占了 50% 耗时，
   说明 0.80 的通过阈值可能偏高，应该用评测数据找拐点。

## 七、这次实测带来的架构级收获

1. **超时参数必须按"最慢负载"设计，而不是平均负载** —— 长短差两个数量级，平均值会骗人。
2. **长文生成一律走流式** —— 这是机制选择，不是参数调整。
3. **超时的真实代价是成本，不只是延迟** —— 重试会重复计费，这个账很容易被忽略。
4. **Function Calling 的可靠性 = schema 正确 + 描述无歧义** —— 后者常被低估。
5. **反思循环是最大的成本黑洞** —— 必须有硬上限，且阈值要数据驱动调优。
6. **同步 HTTP 扛不住分钟级 Agent 工作流** —— 异步 + SSE 是必选项而非加分项。

## 八、面试可直接引用的话术

> **Q: 你用真实模型跑过吗？性能怎么样？**
>
> 跑过，阿里云百炼的 qwen3.8-flash。我专门测了两组数据：短问答 **1.8 秒**，
> 但生成一份近万字的 Listing 方案要 **227 秒** —— 差了 **126 倍**
> （探针脚本 `scripts/bench_latency.py`，结果归档在 `docs/bench_latency_result.md`，可复跑）。
>
> 这个差异直接暴露了一个坑：我最初把超时设成 60 秒，结果长文生成全部超时。
> 更麻烦的是超时后触发重试，**同一个请求被重复计费三次**，成本翻三倍。
>
> 我的修复不是把超时调大 —— 那是跟模型速度赛跑。我改成**流式生成**：
> 流式下超时约束的是"两个 chunk 的间隔"，而不是"整个响应时长"，
> 只要模型持续吐字就不会被判超时。这是机制层面的解法。
>
> **Q: 全链路要多久？**
>
> 实测约 **23 分钟**（1397 秒），5 个子任务加 2 轮反思循环。
> 从 trace 拆解看，**两轮重写占了 50% 的时间** —— 这说明我的 Critic
> 通过阈值（0.80）设得偏严。这正好引出一个设计权衡：
> 阈值高则质量好但慢且贵，阈值低则反之。正确做法是用评测数据找拐点，
> 而不是拍脑袋定。
>
> **Q: 那你怎么保证线上不超时？**
>
> 这也是为什么我的接口层做了**三种模式**：同步、后台任务、SSE 流式。
> 一个要跑 23 分钟的工作流，用同步 HTTP 一定会被网关掐断（Nginx 默认 60 秒超时），
> 所以必须走后台任务 + SSE 推送进度。
